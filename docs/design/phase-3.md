# Phase 3 design: loads, physics and manufacturing checks

Status: the operator approved this design on 2026-11-07. Units 1 to 7, 10 and 11 of §4 are built, and units 8 and 9 are deferred. It was written against commit 1a3dee2. Terms follow GLOSSARY.md. Each phase 3 PR is one numbered unit of §4. §7 lists the questions that are still open.

On 2026-11-08 the operator deferred printability indefinitely, and on 2026-11-09 slicing, print time and cost with it. The slice read its print orientation from printability, so the two go together. Phase 3 is FEA under stated loads and Test mode. Every mention below of printability, `slice`, a print process, print time or cost is a record of deferred work. It is not built, and no unit of §4 builds it.

## Central decisions

1. **The words fix the load case, fixed check code fixes the faces, and any freedom left over goes to the worst case.** A load case is part of a requirement that the person already confirms in one click on the existing page. It names *anchors* (for example "the bores of exactly 2 holes of 5.5 mm" or "the end farthest from the supports"), never a face. The `fea` check turns anchors into mesh regions with rules that do not depend on the model's coordinate frame. Where the words leave a choice open, the check takes the worst case: an unstated direction is solved exactly by superposing 3 unit loads, and tied candidate faces are each solved, with the worst one kept. A count that does not match gives `unknown`. Nobody picks faces, so there is nothing to bias and no extra confirmation step. ADR-0007 records this decision.
2. **Slow checks are demand-driven background jobs, and the signed result store is the queue.** A job is (variant, the checks it runs, the exact inputs they read). Its key is a hash of those three. Its result is a signed file. Missing result plus no in-flight future means "run it". That makes a crash or restart safe with no queue to persist. `score_variant` keeps its signature. It waits up to 20 s, like `confirm_requirements`, and otherwise returns a card that shows `pending`. You poll by calling it again.
3. **Two images.** Agent code builds in the unchanged build image, so variant ids stay stable. Every check runs in a new analysis image layered `FROM` the build image's digest, with gmsh, CalculiX and PrusaSlicer added (ADR-0005). That image's tag goes into check versions and onto the card, not into variant ids.
4. **Test mode has no server-side state.** Every check that decides a requirement runs at one fidelity, whatever the mode. Test mode is agent guidance: pick one variant, propose the requirements that make the slow checks run (a load), get one confirmation, score, and wait. The server's only part is metering.
5. **Each engine has one adapter file, and hand calculations are the exit condition.** The adapters are `kernel/` for OCP, `mesher.py` for gmsh, `calculix.py` for CalculiX and `prusa.py` for PrusaSlicer, which is deferred. `calculix.py` is our own CalculiX input writer and result reader, not pygccx. The operator decided this on 2026-11-07, and §6 gives the reasons. The FEA math, which is consistent nodal loads and the worst direction from eigenvalues, is pure stdlib and has unit tests. The exit condition is a validation suite of 5 hand-calculation cases with stated tolerances, and `uv run verify` runs it.
6. **The material is not always a requirement.** `material_key` stays a scoring argument. When the brief names a material, an optional confirmed `made_of` requirement pins it, and the card says which of the two set the material (§2.2).

```python
REQUIRES = (closed_solid, interference)


def run(subject: Subject) -> FindingWire:
    gate = required_pass(subject, REQUIRES)  # existing pattern, now a helper
    if gate:
        return gate
    material = elastic_material(subject.inputs)  # Known | Unknown(reason)
    case = subject.inputs.load_case()  # one LoadCaseWire: this run is one instance
```

The unit of work is `Applied(check_id, inputs)`. Its `instance` is `sha256(canonical inputs)[:8]`, or `""` for a check that takes no inputs, and `ResultWire` carries it. Each confirmed load case is its own `fea` instance with its own verdict, job key and pending state. Two requirements on the same case, such as a safety factor and a deflection, share one solve. Measure names stay unqualified.

### 2.1 Load cases

`Force = Annotated[Measured, WrapValidator(_positive("[force]")), …]` follows the `Mass` and `Length` pattern. A load case that does not fit this vocabulary becomes an `unchecked` requirement and shows as unverified. The vocabulary grows only from evidence (#49).

**Anchor rules.** These are fixed code in `checks/container/anchors.py`. They are pure functions over the kernel's geometric summary and do not depend on the model's coordinate frame:

| Anchor | Exact rule | Fails closed when |
|---|---|---|
| `Holes(n, d)` | A *hole* is a set of concave cylindrical faces with one common axis line (direction within 1e-6 rad, offset within 1e-6 × extent) whose angular spans add up to ≥ 2π − 1e-3. So concave fillets (90°) and slots are not holes, and a counterbore's coaxial faces are one hole. The hole's diameter is twice its smallest radius. If `d` is given, keep holes with \|2r − d\| ≤ max(0.05 mm, 1% d). Region: the smallest-radius bore faces as `Bore(origin, axis, r, t0, t1)`. | the number kept ≠ n → `unknown`, with a reason that names both counts |
| `hole_axis` | the axis direction shared by the selected holes | the holes are not parallel → `unknown` |
| `LargestFlat` | the planar face(s) of largest area. Region: `Plane(point, normal, tol)`, so faces flush with it come along | none planar → `unknown`. A tie within 1e-6 relative → each candidate is solved and the worst is kept |
| `FlatEnd` | `LONG` axis from the volume inertia tensor. Candidates: the planar faces whose normal is within 1e-3 rad of ±LONG, at each extreme of the solid's projection on LONG | no such face at either extreme → `unknown`. Both ends qualify → both solved, worst kept |
| `FarEnd` | c = area-weighted centroid of the support region, a = unit vector from c to the solid's centre of mass, R = largest reach (p − c)·a of a surface node p. Region: the boundary triangles whose every node reaches at least (1 − 0.005)·R. Reach is measured along a, not in a straight line, so a whole flat end square to a is selected, not only its corners (#95) | c is within 1% of the largest extent from the centre of mass (no end is the far one) → `unknown`. The region has no triangle → `unknown` |
| `OnHoles` | same hole rule as `Holes`, applied to the holes that are not supports | count mismatch → `unknown` |
| `LONG` | eigenvector of the largest principal extent | the two largest principal moments are within 1% of each other (no unique long axis) → `unknown` |

Why the agent cannot bias this:

- **Nobody names a face.** The agent writes geometry and words. The person confirms the words. The check resolves anchors.
- **Unpinned freedom becomes the worst case.** Direction is a subspace, not a vector, so turning the model in its frame changes nothing. Ties between candidates are each solved, so adding a twin face cannot dodge the load.
- **Gaming a count gives `unknown`, never `pass`.** Adding a third hole makes `Holes(2)` resolve to 3.
- **`FarEnd` is the longest lever from the supports.** A geometry trick that moves the far end moves the load further out, which is worse for the agent, not better. That is why the rule measures reach from the supports, toward the centre of mass, and not along a model axis.

**Worst direction, computed exactly.** In linear statics, the stress and displacement at each node depend linearly on the load direction n. Run one unit solve per basis vector of the subspace (k = 1, 2 or 3). At node i, the displacement is u_i(n) = U_i P a and the stress is s_i(n) = S_i P a, where P is the 3×k basis and |a| = 1. The worst values are then:

- **Displacement:** max |u_i| = σ_max(U_i P), the largest singular value of a 3×k matrix.
- **Von Mises:** max σ_vm,i = √λ_max((S_i P)ᵀ M (S_i P)), where M is the 6×6 von Mises quadratic form.

The peak is the maximum over nodes, scaled by |F|. The sign of the load does not matter for either quantity. Closed-form symmetric eigenvalues of size ≤ 3×3 are written in stdlib (`checks/container/elastic.py`, pure, unit-tested against brute-force direction sampling).

**Load application.** Mesh entities come from gmsh's own import of the BREP. Face selection is a geometric predicate on the nodes of the boundary T6 triangles, so OCP face indices never need mapping to gmsh entities. A triangle belongs to a region when all 6 of its nodes satisfy the predicate within 1e-4 × extent. A force is spread as a uniform traction with *consistent* T6 nodal loads: the corner nodes get 0 and each midside node gets A/3 of the triangle's share. Supports fix the 3 translations at every node of the region's triangles.

**Stress at supports.** A rigid bore makes the peak stress there unbounded, and that peak depends on the mesh. Judging it would make every bolted part fail at random. So `max_von_mises` and `safety_factor` are read outside a keep-out of 0.5 × bore diameter around each `Holes` support. The keep-out size is a constant in `fea.py`. The peak inside the keep-out is reported as `support_max_von_mises` and is not judged. This leaves a known gap: a thin neck right at a bolt hole is not judged. A later bolt-bearing domain check will cover it. The card's formula text states the gap.

**Stress at a clamped face.** Fixing every node of a flat support face makes the peak stress next to it too high on short, stocky parts, because the clamp adds a stress concentration that a beam does not have. A 40×10×10 steel beam read about 22% above beam theory at its root (investigation in #108). The operator decided on 2026-11-08 to leave the measurement as it is, since the error is on the safe side, and to say so on the card. When any support of the load case is a flat face (`flat_end` or `largest_flat`), a passing fea result's `reason` ends with `CLAMPED_FACE_NOTE` in `fea.py`: "Peak stress next to a clamped face can read high on short parts, so the stress and the safety factor here are conservative." A support through holes does not carry the note. No number changes, and the 7% stress bound in §2.9 holds for the validation cases, not for a short part.

**Gates.** Each gate gives `unknown` for that load case. The other cases still report.

- The mesh fails, or the fine mesh exceeds 150k nodes.
- The displacement change between the coarse and fine mesh is above 3%.
- The largest displacement is above 5% of the largest extent, which is outside small-displacement theory.
- No yield strength. Then only `safety_factor` is dropped, and displacement still reports.

**Mesh rule** (constants in `mesher.py`, which `fea.py` imports, so the check version covers them): t5 is the 5th-percentile wall thickness from `thickness.py`, which is shared with printability. The coarse mesh uses h = clamp(t5, 0.2 mm, extent_max/20) and the fine mesh uses h/1.5. Both are second-order tetrahedra (C3D10), with `MeshSizeFromCurvature=24`. The validation suite tuned these constants once (PR 4), and they are now frozen in `mesher.py`: t5/2 put the clamped plate over the node cap, and 12 elements per circle left the hole's peak stress noisy to 2.8%.

### 2.2 New requirement kinds (`briefs/model.py`, after phase 2 lands)

*`printed_on` is deferred (2026-11-08). `max_print_time` and `max_cost` are deferred (2026-11-09). Their rows and the process and money bullets below stay as a record.*

| Kind | Target | `deciding_check` | `limits(target)` |
|---|---|---|---|

| `max_deflection` | `MaxDeflection{load: LoadCase, deflection: Length}` | `fea` at instance `load.id` | `Limit("max_displacement", AT_MOST, deflection)` |
| `printed_on` | `PrintedOn{process: ProcessKey}` | `printability` | `()`, so the verdict is the check's verdict, as with `closed_solid` |
| `max_print_time` | `MaxPrintTime{time: Duration}` | `slice` | `Limit("print_time", AT_MOST, time)` |
| `max_cost` | `MaxCost{cost: Money}` | `slice` | `Limit("filament_cost", AT_MOST, cost)` |
| `made_of` | `MadeOf{material: MaterialKey}` | none, because it pins a scoring input | `()` |

- **The material is not always a requirement.** `material_key` stays a `score_variant` argument. When the brief names a material, the agent may propose `made_of`, and the person confirms it with the rest of the set. A confirmed `made_of` pins the material: `score_variant` refuses any other `material_key`, and the error names the confirmed key. The card's `material` field gives the key and says what set it, either the confirmed requirement by id or the agent's argument. So a person can see when a safety factor rests on a material the agent chose. `made_of` lands in a later PR than the `fea` check (§4).

- **One process per confirmed set.** A `ConfirmedSet` validator refuses a proposal that has more than one `printed_on`. It also refuses `max_print_time` or `max_cost` without a `printed_on` (a `BriefRefused` that names the fix). The process is stated once and read by both `printability` and `slice`.
- **Money is USD only.** `UNITS.define("USD = [currency]")`. A cost in any other unit is refused at proposal time. We keep no FX table.
- **Judging** finds the result by `(check_id, instance)`. Rule one is unchanged: the verdict is unknown unless the result is PASS and the measure exists. A load case that did not solve is therefore unknown.
- **The stated error enters the verdict.** `Measure` gains `rel_error`, which is 0 for every existing measure. The host computes it from the check's pure `error_bound(measure)` and never reads it off the wire. Comparisons use three zones:
  - AT_LEAST: pass when v(1−e) ≥ L, fail when v(1+e) < L, otherwise `unknown: within the check's stated error of the limit`.
  - AT_MOST: the mirror image.

  The bounds are the same constants the validation harness enforces (§2.9), so the stated error from the exit condition is the error the verdicts use. With e = 0 this is today's rule.
- `Waiting` is new (§2.6).
- **Safety factor default.** The `PROPOSE_REQUIREMENTS` text says: "propose factor 2 unless the brief states one". It is still the person's number. The page shows it, and one click confirms it.

### 2.3 Table data

*Deferred (2026-11-09): `filament_cost`, `slicer_filament` and the PrusaSlicer profiles. `processes.yaml` goes with the printability deferral (2026-11-08). They stay below as a record.*

**`tables/materials.yaml`** gets new optional fields per row. Each one is `unknown` or `{value, source}`, as today:

- `elastic_modulus` (MPa)
- `poisson_ratio` (dimensionless). Filament datasheets rarely give ν, so the citation may be a handbook for the polymer family, with the page and the quote. That is a real source, not a guess.

`DensityWire` and `Subject.density` are deleted in the same PR, and `mass` moves to `subject.inputs.value(Input.DENSITY)`. `Subject.inputs` raises `Undeclared` when a check reads an `Input` that is not in its `TAKES`. The runner turns that into `unknown`, and a test makes every check run once under a strict fake. `READS` changes type from `measure → table field str` to `measure → Input`. `specs()` validates READS ⊆ TAKES. The host's echo check (rel_tol 1e-9) and its row citation work as today, for every new table value. The host echoes load magnitudes as well. `READS` values are `FromTable(Input) | FromCase(field)`. A `FromCase` echo must equal the confirmed number the host sent, and it cites the requirement id. `evals/briefs/provenance.py` learns this third origin, so every number on a card still traces to a check measure, a table row, or a confirmed requirement.

Phase 2 seam: confirmed values reach the checks through the per-project overlay of ADR-0006, which `get_material` reads. The overlay adds `project-` rows and never fills an `unknown` field of a git row. So a filament with no git row gets E and ν from a confirmed `project-` row, and the citation is the confirmation record. Since [ADR-0009](../adr/0009-an-unknown-value-is-researched-not-left-unknown.md), an unknown E or ν, including an `unknown` field of a git row such as ν for PLA, is researched instead: the server reads it from a quote it fetched, stores it in the overlay as `researched`, and the fea result names the field and its source. fea reports `unknown` only when no source can be verified.

```python
@dataclass(frozen=True, slots=True)

    engines: Engines                     # replaces `kernel`; Engines(kernel, mesher, solver, slicer)
    shape: Shape | Unreadable
    inputs: Inputs                       # replaces `density`
    reported: Mapping[str, ResultWire]
```

`Engines` holds Protocols. Each real implementation lives in exactly one adapter file, and only that file may import or run its engine:

| Adapter | Engine | Surface |
|---|---|---|
| `kernel/` (split from kernel.py, which is at 357 of 400 lines) | OCP | existing ops + `faces(shape) -> tuple[FaceInfo, …]` (plane/cylinder/other, area, centroid, normal or axis+radius+angular span+concave), `inertia(shape) -> Inertia`, `triangles(shape, deflection) -> Triangles`, `ray_lengths(shape, origins, dirs) -> tuple[float \| None, …]` |
| `mesher.py` | gmsh | `tet_mesh(brep: bytes, size_mm: float, node_cap: int) -> TetMesh \| MeshFailed` |
| `calculix.py` | CalculiX `ccx` | our own .inp writer and .frd reader, which runs `ccx`. `solve(mesh, material, fixed: Region, unit_loads: tuple[NodalLoads, …]) -> tuple[NodalField, …] \| SolveFailed` |
| `prusa.py` | prusa-slicer CLI | `slice(stl: bytes, profiles) -> SliceStats \| SliceFailed` (print seconds, filament grams from the G-code header) |

*The `prusa.py` row is deferred (2026-11-09). The analysis image still installs PrusaSlicer, and the adapter is written when slicing returns.*

A test that extends the existing one for OCP walks the AST of `checks/container/*` and fails when any file outside its adapter names `OCP`, `gmsh`, `ccx` or `prusa-slicer`.

**Versioning.** `check_version` also hashes the analysis image tag. The engines' binaries are not Python sources in the closure, so this is the only honest place to cover them. When the image changes, every check version changes, and the reason is that the image really did change.

**Determinism.** A scorecard must serialize to the same bytes when scored twice on one image and one architecture.

- **gmsh:** `General.NumThreads=1`, `Mesh.MaxNumThreads3D=1`, `Mesh.Algorithm3D=1` (Delaunay, not HXT), `Mesh.RandomSeed=1`, pinned wheel.
- **ccx:** `OMP_NUM_THREADS=1`, `CCX_NPROC_EQUATION_SOLVER=1`, the iterative Cholesky solver (SPOOLES peaked at 2.7 GB on a 130k-node mesh, over the 2 GB budget; this one took 0.6 GB), deb pinned through snapshot.debian.org.
- **prusa-slicer:** so `TBB_NUM_THREADS=1` / `OMP_NUM_THREADS=1`, and a determinism test slices twice.
- **Measures:** no rounding. Per-job results are stored and reused (§2.6), so once a job has run, repeating it is a cache read and the bytes are identical by construction.
- **Architecture:** x86 and arm64 may differ in the last bits. That is fine, because the card records `image_digest`, and the validation tolerances do not depend on those bits.

### 2.5 The three new checks

*`printability` was deferred indefinitely by the operator on 2026-11-08. The person knows their printer better than we do, many designs are never printed, and the product's job is the design. `slice` was deferred indefinitely on 2026-11-09, because it read its print orientation from `printability`, and it needs an orientation from somewhere else before it is built. Both stay below as a record. Phase 3 builds `fea` only.*

**`printability`** (`Quick`; REQUIRES closed_solid; TAKES NOZZLE, MAX_OVERHANG, MIN_WALL, BED)

- **Orientation is chosen by the check, never by the agent.** Candidates are the model as built, then up to 6 distinct largest planar faces placed down, ordered by (area descending, normal lexicographic). For each candidate the check computes the overhang area. The pick is the one with the least (overhang_area, height, index).
- **Overhang area:** the area of the triangles whose outward normal is within (90° − max_overhang) of straight down, excluding triangles within 0.01 mm of the bed.
- **min_wall:** the shortest inward ray from up to 20k triangle centroids (picked deterministically by stride) whose hit lies on a face with an opposed normal (dot < −0.5). Hits on a neighbouring face at a concave corner do not count.
- **fits_bed:** the sorted extents of the chosen orientation are within the sorted bed edges.
- **Pass** when overhang ≤ 1 mm² **and** min_wall ≥ MIN_WALL **and** it fits.
- **Measures:** `overhang_area mm^2`, `min_wall mm`, `print_height mm`, `print_down:x|y|z dimensionless`, plus READS echoes `max_overhang_angle deg`, `min_wall_limit mm`, `nozzle_diameter mm`.
- **No process confirmed:** `unknown` ("no confirmed printed_on requirement names a process"). It runs fast, so it runs even without a brief once a process is known.

**`fea`** (`Background(600 s, 2048 MB, tmpfs 768 MB)`; REQUIRES closed_solid, interference). See §1b and §2.1. There is one instance per confirmed load case. An instance passes when its case solved and passed every gate. Otherwise it is `unknown`, with a reason that names the gate that failed.

**`slice`** (`Background(300 s, 2048 MB, tmpfs 512 MB)`; REQUIRES printability; TAKES FILAMENT_COST, SLICER_PROFILES)

It requires printability because it reads `print_down:*` from `subject.reported`. It runs whenever printability is not `unknown`, so a part with a failing overhang still gets a print time.

- Turns the part to the chosen orientation, writes an STL from `triangles()`, and runs prusa-slicer.
- **Measures:** `print_time s`, `filament_mass g`, `filament_cost USD`, and the READS echo `filament_cost_per_kg USD/kg`.
- **Cost is ours:** grams × table price. The slicer's own cost setting is never used.

`suite.CHECKS = (closed_solid, interference, mass, extents, printability, fea, slice)`. The existing REQUIRES-order rule still holds. With the two deferred checks left out, phase 3 ships `(closed_solid, interference, mass, extents, fea)`.

### 2.6 Jobs, the store, background lanes and the scorecard

**Plan** (`checks/jobs.py`, host). Everything here is derived from `CHECKS`, with no second list.

```python
@dataclass(frozen=True, slots=True)
class JobSpec:
    variant_id: str
    brep_sha256: str
    # Quick checks form one job; each Background (check, instance) is its own job
    applied: tuple[Applied, ...]
    budget: Budget
    wire: RequestWire  # projected to the union of the targets' + closures' TAKES
    reads: Mapping[Input, TableRead]

    # sha256(json([brep_sha256, analysis_tag, [spec.version…], wire]))[:20]
    @property
    def key(self) -> JobKey: ...


def plan(
    held: HeldEntry, request: Request, demanded: frozenset[str]
) -> tuple[JobSpec | NotRun, ...]:
    """Quick job always. A Background check gets a JobSpec only if `demanded` (the deciding checks
    of the confirmed requirements, closed under 'slice needs printability') names it. Otherwise it
    is NotRun(check_id, reason='no confirmed requirement is decided by fea, so it did not run')."""
```

The key covers only what the job reads. Changing material reruns `fea`, `slice` and the quick job, because density is in the quick wire. Changing brief wording without changing the load cases reruns nothing.

**Store** (`checks/job_store.py`, host, deliberately *outside* `variants/` so that `TRUST_DIGEST` and every variant id are unaffected):

`<root>/<vid>/jobs/<key>.json` holds the host-parsed `tuple[CheckResult]` (plus the STEP sha for the quick job). `<key>.mac` holds HMAC-SHA256(store key, vid ∥ \0 ∥ key ∥ \0 ∥ bytes). Both are written to a temp file first, then moved into place with `os.replace`.

The server now reads results back from disk, which today's `scorecard.json` never does, so they must be signed: ADR-0003's threat applies. If the MAC check fails, the server treats the result as missing and reruns the job. It never trusts it. Results that all say `unknown` because of the sandbox (Docker unavailable, a usage refusal) are not stored, so they get retried. A timeout or OOM is stored: it is a deterministic outcome for that input. Removing the file is the operator's retry.

**Attempt cap.** Before a background job starts its container, it writes `<key>.attempt`, which holds a count. A finished job removes that file. If a job finds a count of 2 already there, its last two runs were interrupted, for example because the server died. It then stores `unknown: the analysis was interrupted twice` instead of running a third time. This stops one input from looping a server forever. There are no leases: in-flight state lives only in this process's futures, and two processes racing write identical bytes.

**Lanes** (`checks/lanes.py`, the one owner of in-flight state, one instance per server process). This file must not live in `sandbox/`, because `TRUST_DIGEST` hashes `sandbox/*.py` and every variant id would change on each edit to it:

```python
class Lanes:
    """Quick jobs run on the calling thread and hold one of the existing 2 SLOTS. Background jobs
    run on one worker thread (FIFO) and also take a SLOT, so at most 1 slot is ever background and
    a quick score never waits behind FEA. In-flight: dict[JobKey, Future], under one lock."""

    def settle(self, plan: Sequence[JobSpec | NotRun], wait_seconds: float) -> Settled: ...

    #   for each JobSpec: stored and MAC-valid -> Done; in flight -> its future; else meter.admit
    #   then submit. Quick: run now. Then wait on background futures up to wait_seconds total.
    #   Returns Done | Pending | Refused per job.
```

- **Idempotent.** Calling twice gives the same keys. Each key is either one future or one file, never two runs in one process.
- **Two processes** (two sessions on one store) may run the same job. Both write identical bytes through `os.replace`, so the race is harmless.
- **Crash or restart.** Futures are lost, the files remain, and the next `score_variant` recomputes what is missing. There is no queue file and no `running` state on disk to go stale.
- **Orphans.** Background containers carry the existing pid-owned label, so `container.remove_orphans()` already kills those whose server died. Each container has its own wall deadline as well.

**Meter** (`checks/jobs.py`): `class Meter(Protocol): def admit(self, job: JobSpec) -> Admitted | Refused`. Locally it is `Unmetered`. The hosted version charges `Background.wall_seconds` against the account before submitting. A refusal becomes `unknown`, with the meter's fixed reason, for that check's requirements. It is not stored.

**Scorecard model** (`scorecard/model.py`):

- `results: tuple[CheckResult | PendingCheck, …]` in SPECS order. `PendingCheck{kind:"pending", check_id, formula, sources, version}` carries no verdict and no number.
- `RequirementResult` gains `Waiting{kind:"waiting", requirement_id, statement, check_id}`.
- `pending: tuple[str, …]` is derived and validated, like `unverified_requirements` is.

The card is assembled in SPECS order from stored job results. The final card's bytes therefore do not depend on the order or timing in which jobs finished. `CheckRun` loses its single `image_digest` for the build entry and gains `check_image_digest`.

### 2.7 Test mode

- **Server side:** nothing new. There is no mode argument and no second fidelity. Slow checks run when a confirmed requirement needs them. The meter caps spend.
- **Agent guidance** (instructions + `score_variant` description):
  1. Enter Test mode when the person picks a variant or asks "will it hold / how long to print".
  2. Propose the load, print-process and time/cost requirements the slow checks need, in **one** proposal, for one click.
  3. Score that one variant, not all of them.
  4. Call again until nothing is pending.
  5. Report only check results.

  Design and Auto mode get the same slow checks whenever the brief already needs them.

## 5. Tradeoffs accepted

- **Worst-case directions and ties are conservative.** A shelf bracket loaded "down" can fail on sideways bending it would never see. In exchange the agent cannot win by turning the model, and the person never picks a face.
- **Stress inside the fixed keep-out at bolt bores is reported but not judged.** We accept that a thin neck at a hole goes unjudged until a bolt-bearing check exists. The alternative was judging a mesh-dependent singular peak, which fails parts at random. The keep-out is a constant in the check, so the agent cannot move it.
- **A small anchor vocabulary.** Briefs it cannot express become unverified rather than approximated. Coverage grows with evidence.
- **A changed material or process reruns the slow jobs, and job results are kept forever until deleted.** We get a cache with no invalidation logic: the key is the input.
- **Polling through `score_variant`.** The client gets no push notification. The MCP surface stays at +1 tool (`list_processes`).
- **Our own .inp writer and .frd reader,** about 150 lines, instead of pygccx. We maintain the file-format code ourselves. SPEC's stack table records the choice.

## 6. Alternatives considered

- **The agent tags faces in build code** (named faces `load` / `support`). Rejected. It is a deep interface to the wrong actor: the party being graded chooses where the load goes. It hides nothing and opens the main bias channel.
- **The person picks faces in a viewer (#79), per variant.** Rejected for v1. It costs one confirmation per variant per load case, which goes against "friction is a defect", and phase 4 owns the viewer. It is a good later override: an explicit region confirmed by a person could become a fourth `Support` kind.
- **One image with everything.** Rejected. Every engine bump would change every variant id and rebuild every stored entry, and it would add gmsh, ccx and the slicer to the attack surface agent code runs against.
- **A persistent job queue (sqlite / jobs table) with a `running` state.** Rejected. It is a second owner of state that can go stale after a crash. Deriving work from missing signed results gives the same behavior with nothing to recover.
- **New tools `start_analysis` / `get_scorecard`.** Rejected. That would be two ways to get a card. The `confirm_requirements` wait-then-pending precedent already exists.
- **A server-side Test mode flag that selects higher-fidelity FEA.** Rejected. One requirement would get two verdicts depending on mode, and the scorecard would stop meaning one thing.
- **pygccx.** Rejected by the operator on 2026-11-07. Installing it was not the problem. It is not on PyPI, but each GitHub release ships a pure-Python wheel, such as `pygccx-0.3.0-py3-none-any.whl` from 2025-02-18, and `analysis-requirements.txt` could pin that wheel by URL and hash. These are the reasons:
  - It has one maintainer, and the last commit is from February 2025.
  - Its license is GPL-3.0. Importing it into the trusted check code would pull that code toward the GPL if the checks are ever open-sourced or self-hosted.
  - It depends on numpy, scipy and the gmsh API, which adds code to the check image that we do not review.
  - Phase 3 needs only static analysis, a small part of what it covers.

## 7. Open questions and risks

- **gmsh is Debian's 4.8.4, from 2021.** PyPI has no linux aarch64 wheel, so ADR-0005 takes gmsh from Debian, the same version on both architectures. PR 4's hand-calc cases all pass on it, within 2.1% of hand calculations.
- **The material when the brief names none.** The agent's `material_key` then decides safety factors, and the card says that the agent chose it (§2.2). Is that enough, or should a later PR ask the person before a safety factor rests on a material that the agent chose?
- **Revisit OrcaSlicer later.** Its Linux builds need a newer glibc than bookworm. Moving both images to trixie would allow it, at the cost of changing every variant id again and an untested OCP on trixie. PrusaSlicer 2.5.0 is from 2022, and Bambu profiles fit Orca better.
- **Is a 150k-node cap at 2 GB enough** (PR 4 measured 0.6 GB for the solver at 130k nodes with iterative Cholesky) for real brackets with 2 mm walls, or should `fea` get a 4 GB budget, which would leave room for only one container while it runs?
- **FDM anisotropy.** Should `yield_strength` for printed materials become min(XY, Z) when the datasheet gives Z, which is more conservative and honest for parts loaded across layers?
- **Is phase 2 editing `scorecard/model.py`** for candidate values and "waiting on you"? `Waiting` should probably be one concept, covering both "waiting on a check" and "waiting on you".
- **Is a 1 mm² overhang allowance and "no supports" the right default meaning of printable,** or should `printed_on` carry `supports: allowed`?
- **Is the 0.5 × diameter keep-out at bolt bores the right rule?** An engineer should check it against a bolted reference case before it is frozen.

## 9. Alternatives and why the shape holds

Three designs were drafted independently and compared. This design starts from the one whose loads are frame-independent, because that property is the hardest to add later. Another draft resolved load sites against the world axes and the bounding box. The agent picks the model's frame, so it could place a small flat at +x near the supports, and the words on the page would still read correctly to a person who cannot check the frame.

From the other drafts, this design takes `Applied` with `instance`, three-zone verdicts tied to the harness bounds, `FromCase` echoes, the keep-out at rigid bores, the attempt cap, the `bulk | printed` specimen tag, and the OrcaSlicer spike with its stop rule. The keep-out replaced a judged peak at the supports, which was mesh-dependent rather than conservative. Comparing the drafts also showed that `lanes.py` must live outside `sandbox/`, because an edit to any file there changes every variant id.

It leaves these out:

- Quick checks on the job ledger. They add moving parts to the working path and gain little.
- `O_EXCL` leases. They are a second owner of in-flight state, and the attempt cap covers the real risk.
- A `test=True` depth. One requirement should get one verdict, and three-zone verdicts already keep results near a limit honest.
- Rounding measures to 4 significant figures. Cached job results are byte-identical without it.
- Face ids that the agent proposes at Plan time, before any variant exists.
- One image for everything.
- Four new tools.

Two drafts reached the same answers without seeing each other: a closed load vocabulary confirmed on the existing page, exact counts that fail closed, two images with variant ids from the build image only, signed per-job results as both cache and queue, `score_variant` as the poll with no new tools, Test mode as guidance only, and splitting `kernel.py` first. That agreement is the main reason to trust the shape.
