# Onshape and Fusion: how parts would move in and out

Status: research, written on 2026-11-12. Nothing here is built, and nothing is decided. Every recommendation is the research's own and waits for the operator. The section on contradictions lists the calls the operator must make first. Citations of repository files were read at commit 32e9e1a, so line numbers may have moved. Vendor facts were read from the linked pages in November 2026.

As of November 2026, the only workable way to move parts between our product and Onshape or Fusion is for our own server to call each vendor's cloud API under the person's OAuth grant. What moves in either direction is a plain B-rep solid in STEP, not an editable design. Vendor MCP servers cannot do this job. Onshape's only official MCP server writes FeatureScript and has no export tool. Fusion's own MCP server listens on 127.0.0.1 on the person's desktop. Fusion Compute MCP, the one cloud server that touches geometry, is a public beta, and its token and its short-lived export link stay inside the person's own MCP client, which our web chat agent does not have. **Recommendation:** build Onshape first, as SPEC phase 5 already plans. Put an "Import from Onshape" picker beside the Files "+" that pins a document version and feeds STEP into the existing sandbox ingest as a new origin, and put a "Send to Onshape" action beside Download that uploads the STEP the checks measured. Onshape's quota sets the commercial shape. Calls from a private OAuth app count against the app owner, at 2,500 to 10,000 calls per user per year. Calls from a public App Store app are not counted. So an App Store listing is the scaling path, and it takes weeks. Fusion comes second, through Autodesk Platform Services (APS): OAuth, Data Management to browse, Model Derivative to turn a Fusion version into STEP, and a Data Management upload to send STEP back as a plain file that the person opens in Fusion. Model Derivative translations are billed in Flex tokens, and the research could not find what a token costs. Before any build starts, the operator must settle contradictions in the product's own records. The sharpest is this: a 2026-11-07 correction says to work through vendor MCP servers with no vendor accounts on our server, while SPEC phase 5, ADR-0012 and a 2026-11-10 comment all assume that our server holds Onshape credentials.

## Only the vendors' cloud APIs move geometry server to server

The product already supports the baseline route, plain file exchange. A signed-in person drags a STEP or STL file into the project. The upload counts as their confirmation, and the file runs through a no-network sandbox ingest that keeps valid solids, converts units to millimetres and stores a content-addressed BREP ([ADR-0012 L13–23](../adr/0012-a-supplied-part-is-read-by-the-build-and-never-graded.md); [src/cad/uploads/store.py L39–69](../../src/cad/uploads/store.py)). On the way out, the workspace Download menu offers STEP AP214, binary STL and 3MF, written from "the BREP the checks measured, in millimetres" ([src/cad/operations/exports.py L16–22](../../src/cad/operations/exports.py)). This route needs no vendor account and works with both vendors today. It costs the person a manual round trip, and it records no link to the vendor document.

Every other route was tested against one question: can a hosted server get STEP bytes from a person's Onshape or Fusion account, and put STEP bytes into it? The table gives the answer for each route.

| Route | Onshape | Fusion | What it carries | Verdict |
|---|---|---|---|---|
| Plain file exchange (shipped) | Person exports and uploads by hand | Same | Solid only | Works now. Manual, with no pin and no update link |
| Our server plus the vendor cloud API, with OAuth | REST translations in both directions | APS Data Management, Model Derivative, Manufacturing Data Model (MFG) | Solid in both directions, plus metadata to read | **Recommended** |
| Official vendor MCP servers in the person's client | FeatureScript MCP only (Labs, no export) | Local Fusion MCP (loopback), Fusion Data MCP (no geometry), Fusion Compute MCP (beta) | Solid only, and only through the agent | Not viable as the main route |
| Community MCP servers | Local process with the user's own keys or OAuth app | Desktop add-in plus a local socket | Solid only, and the file lands on local disk | Not viable for a hosted server |
| Desktop add-in or in-CAD extension | Extension iframe (SPEC puts it out of scope) | `.bundle` add-in (SPEC puts it out of scope) | Can write native features | Defer |
| Server-side Fusion scripting | Not applicable | Automation API, 3.0 Flex tokens per processing hour | Can write a native design | Later, optional |

The vendor MCP route fails on documented facts, not on taste. PTC's one official server, the FeatureScript MCP Server, launched in August 2026 under Onshape Labs (early access). It exists to "write, test, and debug" custom features, and its page lists no tool that reads assemblies, exports parts or imports geometry ([Onshape FeatureScript MCP](https://www.onshape.com/en/features/featurescript-mcp)). A general "Onshape MCP server" has been announced with no date ([Onshape blog](https://www.onshape.com/en/blog/ai-artificial-intelligence-cloud-native-cad-pdm-platform)). On the Autodesk side, the local Fusion MCP is reachable only at **`http://127.0.0.1:27182/mcp` while desktop Fusion is open**, with no authentication ([Autodesk help](https://help.autodesk.com/cloudhelp/ENU/ADSKMCP-FusionDesktopMcp/files/ADSKMCP_FusionDesktopMcp_connecting_to_the_fusion_mcp_server_html.html)). Fusion Data MCP handles hubs, projects, folders and items, not geometry ([Autodesk Fusion MCPs overview](https://help.autodesk.com/cloudhelp/ENU/Fusion-MCP/files/FMCP-OVERVIEW.htm)).

Fusion Compute MCP can export STEP and STL from headless Fusion sessions in Autodesk's cloud. It is a **public beta**. It needs the person's Autodesk ID with a valid Fusion licence and a Fusion Team hub, and its tools "may change" ([Autodesk help](https://help.autodesk.com/view/ADSKMCP/ENU/?guid=ADSKMCP_FusionComputeMcp_connecting_to_the_fusion_compute_mcp_server_html); [Autodesk developer blog](https://blog.autodesk.io/fusion-compute-mcp-server/)). A secondary source reports a cap of 2 concurrent sessions per user, with a 1-hour session limit and a 15-minute idle timeout ([ChampionXperience](https://blog.championxperience.com/autodesk-fusion-compute-mcp-ai-cad-manufacturing/)).

The structural problem sits on top of these limits, and the product's own issue tracker already names it. MCP servers cannot call each other, so only the agent sits between ours and the vendor's. No vendor MCP tool hands STEP bytes to the agent, and passing a file through the model is impractical above tens of kilobytes. These findings are recorded in the issue that tracks reading context parts from Onshape and Fusion ([laminarityai/cad#60](https://github.com/laminarityai/cad/issues/60)), and the vendor pages above confirm them. Our own web chat agent is "a client of the same MCP tools as any outside client" ([src/cad/chat/turn.py L3](../../src/cad/chat/turn.py)). It connects to no vendor MCP, so an MCP-only design leaves the web app with nothing.

Community servers do not close the gap. hedless/onshape-mcp (164 stars) has 45 tools but no licence file, and its export tools return only a translation id. altendky/onshape-mcp makes each user register their own OAuth app and "does not provide a public hosted MCP server" ([hedless/onshape-mcp](https://github.com/hedless/onshape-mcp); [altendky/onshape-mcp](https://github.com/altendky/onshape-mcp)). The community Fusion servers copy BlenderMCP's pattern: a desktop add-in with an unauthenticated local socket, which its authors say to keep off networks ([faust-machines/fusion360-mcp-server](https://github.com/faust-machines/fusion360-mcp-server)).

The established integrators confirm the choice. SimScale is the closest analogue to our hosted web app. Its import widget opens an Onshape Connector App in which the person authorizes once and then browses their documents to pick a part ([SimScale](https://www.simscale.com/partners/onshape)). No AI CAD product found in this research moves geometry through an MCP server. Generators such as Zoo export STEP for a manual import ([Zoo docs](https://zoo.dev/docs/zoo-design-studio/features/data-management/export)), and copilots such as Adam live inside the CAD tool as an Onshape store extension or a Fusion add-in ([Adam Copilot](https://adam.new/copilot)).

## Every workable route carries a solid; an editable design needs a second code target

STEP is the common currency, and it carries geometry, not intent. Onshape documents its STEP import as "AP203, AP214, and AP242 (**geometry and face color only**)", and calls Parasolid its "preferred import format" ([Onshape supported formats](https://cad.onshape.com/help/Content/translation.htm)). An import lands as one Import feature, and "Imported geometry does not carry with it the parametric history" ([Onshape help](https://cad.onshape.com/help/Content/Document/working_with_imported_cad.htm)). Fusion behaves the same way: STEP exchanges geometry, and the person adds direct features on top ([Autodesk blog, 2025](https://www.autodesk.com/products/fusion-360/blog/import-step-file-into-fusion-360/)). Open-source OpenCascade (OCCT), the kernel under build123d, writes STEP AP214, AP203 and parts of AP242, but it writes neither Parasolid nor SAT. Only commercial converters such as CAD Exchanger bridge that gap ([OCCT STEP guide](https://occt3d.com/dev/doc/overview/html/occt_user_guides__step.html); [CAD Exchanger](https://cadexchanger.com/brep-to-x-t)). Our STEP therefore arrives in either tool as a dead solid. Its part name is also "result", because the exporter writes that fixed header name and no material, colour or brief name ([src/cad/checks/container/kernel/ocp_kernel.py L258–279](../../src/cad/checks/container/kernel/ocp_kernel.py)).

An editable design can be written, but only by generating each vendor's native script. A build123d program cannot be translated into either one. Onshape's REST API accepts features as internal, versioned JSON, and the docs warn that "parameters may change at any time". Face and edge references need deterministic ids that "may change" when the model changes ([Features API guide](https://onshape-public.github.io/docs/api-adv/featureaccess/); [Associativity guide](https://onshape-public.github.io/docs/api-adv/associativity)). FeatureScript is the better Onshape target, and PTC is steering language models toward it. In Fusion, the API can build a full timeline on the desktop, and the Automation API can run the same scripts headless at **3.0 Flex tokens per processing hour** ([APS blog](https://aps.autodesk.com/blog/design-automation-api-fusion-now-generally-available)). Each option means the agent writes a second program in a second language, and our checks never measured that program's output. That would break the product's core claim, that checks decide whether a design is good ([AGENTS.md L11](../../AGENTS.md)), unless the result were re-exported and re-scored.

Reading a parametric design is easier, but not useful for checking. Onshape returns feature lists, sketches, variables, configurations, mates, the BOM and mass properties. Re-running those features in OCCT would mean re-implementing Onshape's feature semantics. Even the mass and material Onshape reports cannot grade anything, because a check's numbers must come from our tables by exact key ([AGENTS.md L12](../../AGENTS.md)), and a supplied part is never graded at all ([ADR-0012 L29](../adr/0012-a-supplied-part-is-read-by-the-build-and-never-graded.md)). Vendor metadata is display-only context.

**Recommendation:** treat both connectors as solid exchange with provenance, and do not promise editable designs. The product's own risk register says "We win on checks the agent cannot change and on variant comparison, not on having an Onshape integration" ([SPEC.md L158](../../SPEC.md)). Both vendors shipped their own agent routes to native features in 2026, so competing on feature authoring means meeting them on their own ground. One cheap improvement is worth making first. Write the brief and option name into the STEP product name and keep millimetres, so the part arrives in Onshape or Fusion with a meaningful name instead of "result".

## Onshape: a private OAuth app works today, and the quota forces an App Store listing

Authentication is standard. A hosted app that acts for many users must use the OAuth2 authorization-code flow, because an API key "will only perform operations on behalf of the Onshape user who generated" it ([Onshape help](https://cad.onshape.com/help/Content/Plans/developer-myaccount.htm)). The endpoints are `oauth.onshape.com/oauth/authorize` and `/oauth/token`. **Access tokens last 60 minutes, and refresh tokens last "for the lifetime of the user's grant"**. Every refresh returns a new refresh token, so the server must store both tokens. PKCE is not mentioned ([Onshape OAuth guide](https://onshape-public.github.io/docs/auth/oauth/)). The product needs the `OAuth2Read` scope to pull parts and `OAuth2Write` to upload and to create documents and versions. It does not need `OAuth2Delete` ([OpenAPI spec](https://cad.onshape.com/api/openapi)). Redirect URLs must use HTTPS, except for the desktop app type on `http://localhost`. The hosted app's `https` public URL fits, but local development needs a desktop-type app or a tunnel. Enterprise customers use `companyName.onshape.com/api` as their API host ([API intro](https://onshape-public.github.io/docs/api-intro/)), so a host allow-list must accept those subdomains.

Import maps cleanly onto Onshape's data model. Every path is `/d/{did}/{w|v|m}/{id}/e/{eid}`. Versions and microversions are immutable. Part ids are valid only within one version, because "When the model changes, the ID may change" ([API intro](https://onshape-public.github.io/docs/api-intro/); [Associativity guide](https://onshape-public.github.io/docs/api-adv/associativity/)). So the pin is (document, version, element, part, configuration). The asynchronous export endpoints accept a workspace or a version, not a microversion. To export one part from a multi-part Part Studio, the documented call is the generic `POST /partstudios/.../translations` with `formatName: STEP` and `partIds`. The newer `/export/step` route (May 2025) takes `stepUnit` and `stepVersionString` (AP242) but has no `partIds` field. Either way the server polls `GET /translations/{id}` with backoff until `DONE`, then downloads the file from `/documents/d/{did}/externaldata/{fid}` ([OpenAPI spec](https://cad.onshape.com/api/openapi); [Import & Export guide](https://onshape-public.github.io/docs/api-adv/translation/)). A re-import from a newer version must find the part again by `partIdentity`, by name or through `idtranslations`, not by the old id.

Export to Onshape is a multipart upload. `POST /documents` creates a document. `POST /blobelements/d/{did}/w/{wid}` with the STEP file, `translate=true` and `storeInDocument=true` creates a translated Part Studio. A later revision calls `uploadFileUpdateElement` on the same blob, and Onshape then reapplies the person's downstream features "where possible" ([OpenAPI spec](https://cad.onshape.com/api/openapi); [Onshape help](https://cad.onshape.com/help/Content/Document/working_with_imported_cad.htm)). The UI help says that an updated blob propagates to the Import feature. The API docs do not say that the API call behaves the same way. `useFileNameToSetSinglePartName` (July 2024) names the imported part after the file ([Onshape changelog](https://onshape-public.github.io/docs/changelog/)). Webhooks exist, including `onshape.model.translation.complete`. Their HMAC signing keys are set by a Company or Enterprise admin ([Onshape help](https://cad.onshape.com/help/Content/Plans/webhooks.htm)), so a product serving individuals should poll first and treat any webhook as a hint to re-fetch.

The limits shape the product more than the endpoints do. The annual quotas are **2,500 calls per user on Free and Standard, 5,000 on Professional and 10,000 per full user on Enterprise**. A request over quota gets HTTP 402. Per-endpoint rate limits are unpublished and return 429 with `Retry-After`. The rule that matters most: "Private app calls count against the app owner's limit, not the end user's", while "OAuth2 calls from public App Store apps" are not counted at all ([API limits](https://onshape-public.github.io/docs/auth/limits/)). One import (list parts, submit, one to three polls, download) costs roughly 3 to 6 calls. One send costs about the same. A private app owned by a single Professional seat therefore covers on the order of a thousand imports and sends a year across every user combined.

A public listing needs OAuth2, at least 5 beta testers, a developer agreement, a support channel with ticket response obligations, security questions (SOC 2, CAIQ) and a final QA of "up to a week" under a code freeze ([Launch checklist](https://onshape-public.github.io/docs/app-store/checklist/)). Developer licences are free on request. The docs never say whether a person outside the owner's company can authorize an unlisted app at all. Store entries stay "viewable only to you and any internal teams" until published ([Onshape help](https://cad.onshape.com/help/Content/Plans/developer-myaccount.htm)).

Two more facts bear on cost and terms. First, the **Free plan is non-commercial and makes every document public**, under a broad licence to third parties ([Onshape Terms](https://www.onshape.com/en/legal/terms-of-use); [Onshape pricing](https://www.onshape.com/en/pricing)). Anything "Send to Onshape" writes into a Free account becomes public, so the person needs a warning first. Paid seats cost $1,500 (Standard) and $2,500 (Professional) per user per year. Second, the Terms of Use say that customers own their Content as their confidential information. They also ban automated "data mining, data gathering or extraction" and building "a similar or competitive service offering" ([Onshape Terms](https://www.onshape.com/en/legal/terms-of-use)). The binding API Agreement appears only on first sign-in to the developer portal and was not read. Whether an AI CAD generator counts as "competitive" is a question for that text and for a lawyer. Onshape no longer maintains a Python client. The public OpenAPI document (version 1.223, served without sign-in) is the practical base for typed models covering the roughly 15 operations needed ([onshape-public on GitHub](https://github.com/onshape-public)).

## Fusion: the APS route works without a desktop, at a metered price, and lands STEP as a plain file

APS gives a hosted server a complete path that needs no desktop install. Register a private "Traditional Web App" client and use the authorization-code flow with PKCE (S256 is supported). Request `data:read data:create data:write`. **Access tokens last 60 minutes and refresh tokens 15 days**, so a person who stays away longer than that signs in again. A refresh can narrow scopes but never widen them ([APS docs](https://aps.autodesk.com/llms-full.txt); [Get Token](https://aps.autodesk.com/en/docs/oauth/v2/reference/http/gettoken-POST/)). Fusion Team data "requires the use of a 3-legged OAuth2 token" ([Upload tutorial](https://aps.autodesk.com/en/docs/data/v2/tutorials/upload-file/)). No page found requires a Fusion hub admin to provision the app, as BIM 360 does. Since the business model change, every APS app must sit in a developer hub inside an Autodesk Team, and apps not migrated by 18 February 2026 were suspended ([APS business model](https://aps.autodesk.com/blog/aps-business-model-evolution)). Autodesk publishes no official Python SDK, only .NET, Node and Java SDKs generated from `aps-sdk-openapi` ([autodesk-platform-services](https://github.com/autodesk-platform-services)).

Import has two candidate APIs, and the Collaborative Editing rollout decides between them. Data Management walks hubs, projects, folders, items and versions. A Fusion design version has the extension type `versions:autodesk.fusion360:Design` and a URN ending in `?version=N`, which is the natural pin ([DM basics](https://aps.autodesk.com/en/docs/data/v2/overview/basics); [MFG v2](https://aps.autodesk.com/en/docs/mfgdataapi/v2/reference/queries/componentversion)). **Model Derivative translates F3D to STEP (AP203, AP214 or AP242), IGES, STL and OBJ** on every hub type, through `POST /modelderivative/v2/designdata/job`, a manifest poll and a signed download ([Supported translations](https://aps.autodesk.com/en/docs/model-derivative/v2/developers_guide/supported-translations/); [Job POST](https://aps.autodesk.com/en/docs/model-derivative/v2/reference/http/jobs/job-POST/)). The Manufacturing Data Model GraphQL API can generate a STEP derivative per component and return a signed URL. Its v3 has been generally available since 7 November 2025, but it is "exclusively available to users with Collaborative Editing Hubs", and v2 "will be deprecated soon" ([MFG v3 overview](https://aps.autodesk.com/en/docs/mfgdataapi/v3/developers_guide/overview); [MFG v2 overview](https://aps.autodesk.com/en/docs/mfgdataapi/v2/developers_guide/overview)). Collaborative Editing renames things: "what used to be called milestones in Fusion are now versions, and what used to be called versions are now changes" ([Fusion help](https://help.autodesk.com/cloudhelp/ENU/Fusion-Designs/files/TC-COLLAB-EDIT.htm)). The rollout was still in progress in September 2026, and no page says how a Data Management version maps onto a Collaborative Editing "change". Model Derivative is the common path while hubs migrate. How it handles designs that reference other documents is undocumented.

Export into Fusion is cheaper and less satisfying. The documented upload flow has six steps: create a storage location, get a signed S3 URL, PUT the bytes, complete the upload, then create an item, or a new version of an existing item ([Upload tutorial](https://aps.autodesk.com/en/docs/data/v2/tutorials/upload-file/)). It stores the STEP as a generic `items:autodesk.core:File`. No documented API turns that file into a native Fusion design. Autodesk staff said in 2017 that Fusion Team "does not have options to create a Fusion Design from uploaded files", and the person converts the file by opening it in Fusion ([Autodesk forum](https://forums.autodesk.com/t5/fusion-design-validate-document/fusion-in-browser-question-step-file-import-possible/m-p/7484443)). That evidence is old, and whether a Collaborative Editing hub converts an API upload in 2026 is unknown. The only documented server-side way to produce a native design is an Automation API work item that imports the STEP and saves it. The pages read do not document saving to a hub from Automation, and the PAT authentication it used is being removed, so work items must carry the user's 3-legged token ([APS blog](https://aps.autodesk.com/blog/use-fusion-automation-api-without-pat)).

Cost is where Fusion differs from Onshape. Since 8 December 2025, APS has run a Free tier with monthly caps on four "rated" APIs, and **exceeding a cap suspends that API until the next month**. Above that sit paid Flex tokens (minimum 100, expiring after 12 months) or Pay as You Go ([APS business model](https://aps.autodesk.com/blog/aps-business-model-evolution); [APS notice](https://aps.autodesk.com/node/3776)). Model Derivative and Automation are rated. Data Management, OSS, OAuth and Webhooks are not, so sending STEP into Fusion costs nothing, while every import translation is metered. MFG v3 became metered on 17 August 2026. The included usage pools at the Team that owns the APS app, which suggests that our Team pays for its users' exports, not the users' own subscriptions ([APS pricing note](https://aps.autodesk.com/node/3881)).

The research could not read the per-job token rates or the Free-tier caps, which are images or blocked pages. A third-party transcription gives 0.5 or 1 token per Model Derivative job, but it conflicts with other figures ([Licenseware](https://wiki.licenseware.io/catalog/rules/autodesk-autodesk-platform-services-via-flex-model-derivative-api-0-5-or-1-token-per-job/)). The dollar price of a token is unknown. For terms, Autodesk's December 2025 revision says that "you own your content" and "may train on your models and data", as long as you do not "copy or reverse engineer Autodesk products" ([Autodesk News](https://adsknews.autodesk.com/en/?p=55264)). Whether an AI CAD product "replicates Autodesk functionality" is open to interpretation ([AEC Magazine](https://aecmag.com/business/rewriting-the-rules/)), and the APS Terms page itself returned 403.

## The recommended build plugs into seams already on main

The repository already holds most of a connector. Ingest accepts STEP bytes from any source, and `PartOrigin` is a discriminated union that has room for a new arm ([src/cad/context_parts/model.py L52](../../src/cad/context_parts/model.py)). The person-only upload handler is a template for a confirming handler ([src/cad/server/uploads.py](../../src/cad/server/uploads.py)). The export lane already stores the STEP the checks measured and answers "pending, ask again" while it works, which is the shape of an asynchronous vendor job ([src/cad/geometry/exports/lane.py L14–45](../../src/cad/geometry/exports/lane.py)). `research/fetch.py` already refuses non-global addresses on every redirect, pins the resolved address and enforces a per-read deadline, and its transport is injectable for recorded vendor responses ([src/cad/research/fetch.py L93–193](../../src/cad/research/fetch.py)).

Some pieces are missing. The repo has no OAuth client code, no per-account secret store and no encryption: signed records give integrity, not secrecy. It has no authenticated outbound client and no job that survives a restart ([docs/design/deployment-aws.md L156](deployment-aws.md)). Agent-written code runs on the same host as the data ([deployment-aws.md L13](deployment-aws.md)). An Onshape refresh token lasts as long as the person's grant, so storing it unencrypted is a real exposure. This is secrecy, not the tamper-proofing that operator direction says to skip. The order below is a **recommendation**, not a decision. Each step is small enough to verify live before the next one starts.

| Step | Work | Repo seam it uses or adds | Proven by |
|---|---|---|---|
| 0 | Operator settles the contradictions in the next section. Amend SPEC; write an ADR for vendor credentials, authenticated outbound calls and sending to a third party; amend ADR-0004 and ADR-0012 for vendor origins | `docs/adr/`, SPEC phase 5 and out-of-scope list | Operator approval |

Several choices in that order are deliberate. The import job should use the export-lane pattern and not `checks/lanes.py`, because the lanes are model-checked with TLA+ and a vendor job does not belong in the check queue. A person-started import should count as the person's confirmation, as an upload does. An agent-started import would be a proposal that waits on the card, which is why step 8 waits for an ADR amendment. Connectors run in the hosted app only, because the stdio server mounts no upload routes ([src/cad/server/app.py L33–60](../../src/cad/server/app.py)).

Vendor API time is not container time, so `AccountMeter` will not count it. A per-account guard on vendor calls is new work that SPEC's "Onshape API limits" risk already anticipates ([SPEC.md L166](../../SPEC.md)). Large vendor assemblies will meet the 64 MiB body cap and the 60-second, 2 GB ingest limit, as large uploads already do ([src/cad/sandbox/container.py L18–36](../../src/cad/sandbox/container.py)). The fit check is useful for imported parts today. Build code still cannot read a supplied part with `part(id)`, because that step of ADR-0012's delivery plan has no code on main.

## Conclusion

The research reframes the integration. Its value is not editing. It is a frictionless round trip with provenance: a part read at a pinned vendor version, confirmed by the person who picked it, measured by our checks, and sent back as the exact solid those checks graded. The vendors' own AI tooling is aimed at writing native features, so this is the ground SPEC says we win on. It is also why this report recommends that the operator reverse the 2026-11-07 MCP-only correction rather than work around it. Vendor MCP servers keep the credential and the bytes in the person's client, and our web chat agent, which every web-app user talks to, would never see either.

The deciding constraints are commercial, not technical. On Onshape, the quota rule turns an App Store listing from a distribution choice into the condition for having more than a handful of users. SPEC's line against the extension panel need not change, but the listing work belongs in the plan from the start. On Fusion, the build is no harder than Onshape's. Every import is a metered translation at a price nobody has read yet, and every send lands as a file the person must open by hand. One afternoon of live tests and a few emails to the vendors will settle more of this than more desk research.
