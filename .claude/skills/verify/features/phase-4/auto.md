# Auto

The server holds an Auto run. There are no modes. The agent calls `auto_start` when a scored option fails a confirmed requirement that a check decides, then `auto_revise` with each new revision of the code, until the server returns `Stopped`. The server refuses `auto_start` with no web app conversation, with no confirmed requirement that a check decides, while a proposal on the brief waits for the person, and while a stop holds the conversation. A run stops when every checked requirement passes, when a call proposes requirements or a row waits on a confirmation, when the agent calls `auto_ask`, when the account's usage cap refuses a build (`AccountLimit`), or when the person presses Stop. `bounds_conflicts` stops a run before any build, and the confirmation page warns of the same conflict before the person confirms.

Every stop holds the conversation. `record_event` moves the run from the conversation's `auto_run` to its `stopped_run`, and `bind` gives every later tool call that run. So the server refuses `build_variant`, `score_variant`, `auto_revise` and `auto_ask` with `RunStopped`, and `auto_start` with `RunRefused`, before any container starts. Only the chat lifts the hold, in `Chat._begin`, when it records the person's message or delivers a page answer. `GET /v1/conversations/{id}` shows `auto_run`, `stopped_run` and the last `run`. `AutoHold.tla` in [protocol-models](../../../protocol-models/SKILL.md) checks the hold.

Design: `docs/design/phase-4.md` §1b, §2.5 (ADR-0010) and §2.7 (`AccountMeter`). Units 7 and 9 of §4.

## The chat's part

The chat agent runs the loop ([Chat](chat.md)). The server holds the rule, and the chat holds none:

- After every tool call it reads the run's signed log. When the run has stopped, whoever stopped it, it posts a `stop_report` event, with the server's reason and report, and ends the turn. The person's Stop while a turn runs is reported the same way, and the server refuses the agent's next call.
- When the agent ends a message with the run still running, it posts a `driver` reminder to call `auto_revise` or `auto_ask`, at most three times in a turn. Then the turn ends and the run stays Running.
- A message that continues a run is watched too. A run that stopped before the message was reported by the turn that stopped it.

## The checks §4 gives units 7 and 9

- Unit 7, Auto core: table tests for all pass, pending not counting toward all pass, proposing requirements stopping the run, `auto_ask` stopping it with the agent's note, and a cap refusal stopping it with `AccountLimit`. A scripted driver that keeps calling after `Stopped` is refused with no container started. An agent measurement cannot change `step`.
- Unit 9, conflict exit eval: on "fits in a 20 mm cube, PLA, at least 50 g" the confirmation page warns of the conflict, and the run stops with `NeedsPerson(conflict)` and its `Bounds` before any build. On a stiffness-versus-mass brief the agent stops and reports within 6 builds under the run, with a note that names both requirements.

## How to get to it

- **In the web app, live.** Start `cad-http` from the checkout on a live model, as in [Chat](chat.md). Ask for a part with a stated mass limit, such as "A round drink coaster for my desk, 90 mm across. It must weigh at most 8 g." The agent builds every option under a number the person states before they confirm it, so the first options pass. On the chat's Confirm card, type a tighter number with its unit, such as "4 g" when the options measure 6.31 g, and press Confirm. The agent scores the options against the confirmed number, calls `auto_start` and revises with no pick from the person. The chat shows the `Auto run` section with a Stop button. The page reads the conversation every 3 s and a run can pass within seconds of its start, so press Stop as soon as the section reads Running. The section reads "Stopped · you stopped it", the chat shows the stop report, and the agent's next call gets `RunStopped`. A run that passes first holds the conversation too, and its section reads "Stopped · every checked requirement passes". Under either hold the server refuses the agent's `build_variant` with `RunStopped` and its `auto_start` with `RunRefused`. Send a message. `GET /v1/conversations/$CID` then shows `stopped_run` as `null`, and the agent may start a new run when a confirmed number fails again. After a Confirm the agent sometimes revises each option with `build_variant` and starts no run, so no `Auto run` section shows. State a tighter number in a message and tighten it again on the card. Cost: live model, Docker, browser.
- **Through the chat, scripted.** Start `cad-http` as in [Chat](chat.md) and post one message to a script that calls `create_brief`, `propose_requirements`, `ask_to_confirm`, `auto_start`, then `auto_revise` with the plate code. The stream ends with `stop_report` (reason `all_pass`) then `turn_ended`. The run log under `<account base>/projects/` shows `auto_start`, at least one `auto_revise` and `Stopped`.
- **The person's Stop.** While the script's turn runs, `POST /v1/auto/$RUN/stop` with the person's cookie. The stream shows the next call refused and a `stop_report` with reason `stopped_by_person`, and `GET /v1/conversations/$CID` shows `stopped_run` set to the run. A Stop pressed while a build under the run is still running adds "A build was still running when the run stopped, and it is not counted." after the build count. A build whose container returned is counted already, also when its set join is refused or its checks still run. `tests/auto/test_count.py` covers each case.
- **With a headless client.** Confirm a brief (browser as the person), `auto_start`, `auto_revise` with the plate code, then call `auto_revise` again after `Stopped` and show the refusal with no new container (`docker ps -a --filter label=cad.sandbox` before and after). Cost: docker + browser.
- **The conflict exit, in process.** `uv run python evals/briefs/run.py --driver inprocess --briefs ~/cad-evals/briefs --out <dir> --only conflict-cube` builds the hosted app in the process, starts a conversation, posts the brief through the chat routes and lets the scripted person confirm the page. The default model is `scripted`, a script built from the brief's grader. The line it prints is `conflict-cube: pass, conflict, 0 builds, 0 variants`. `<dir>/conflict-cube/auto.json` holds the `Bounds`, the run that holds the conversation (`stopped_run`, the run's own id), `variants` 0 and `containers` 0 (the account's meter holds no `reserve` line), and `events.json` the stream. Run it with `--opener "$CAD_BROWSER/bin/open"` to watch the confirmation page in the browser, where B's warning shows the same pair. Cost: no model, no Docker, about 2 s.
- **The same, on a live model.** Add `--model claude-haiku-4-5-20251001`. The driver reads the key from `~/.config/cad/anthropic.env` when `ANTHROPIC_API_KEY` is not set, as `cad-http` does. With no key in either place the driver exits 1 and names `ANTHROPIC_API_KEY` before it builds anything. The live agent sees only the brief text. It stops with `conflict` only when it names a material the table holds (`made_of` with a `list_materials` key) because the server reads the density by exact key (ADR-0009); a generic key such as `pla` has no density, so the run starts and the agent must find the conflict itself. `propose_requirements` tells the agent to call `list_materials` first; four of four runs before that sentence missed the conflict. Cost: live, under a minute.
- **The stiffness-versus-mass brief** is `conflict-stiffness-mass` in the same set. The scripted run stops with `agent_asked` and no build. On a live model the run must stop with `agent_asked` within 6 builds (`within_builds`, every build under the run, whichever tool made it) and a note that names both requirements and says they conflict, which `autoresult.judge` checks by keyword from the `expect` block in the brief's grader. Read the note too: an agent that stops because a material value is missing has not found the conflict. `prusament-pla` now cites a Poisson's ratio of 0.34 (Song et al. 2017, Table 6), measured on printed unidirectional PLA specimens, so `fea` decides on it. On Haiku, three of three runs still failed: one picked `bambu-pla-basic`, which has no Poisson's ratio, and stopped for it after 8 revisions; one stopped after 6 revisions to ask about build failures; one used `prusament-pla`, `fea` decided, and the note named both requirements and the conflict, but after 9 revisions, more than 6.
- The conflict warning is built and has its recipe in [Briefs](../briefs.md) (Conflict warning).

`uv run pytest tests/evals/test_inprocess_driver.py -q` runs the in-process driver on a cube brief in the test's own words (a stop with `Bounds`, the conversation held by the run, no variant, no container), a brief that agrees, a failed expectation, and a live model with no key. `uv run pytest tests/chat/test_auto_driver.py -q` runs a run to all pass, a run stopped by `auto_ask`, a call refused after `Stopped`, the person's Stop in a turn, and the reminders. `uv run pytest tests/conversations/test_hold.py tests/auto/test_stop_holds.py -q` covers the hold: every stop holds, each agent call after it is refused, a crash before the conversation write heals on the next call, an agent token cannot stop a run, and an old record with `mode` still reads. `tests/chat/test_auto_driver.py` and `tests/chat/test_answer_wakes.py` show the person's message and page answer lifting the hold, and a restart's rerun of a delivery keeping a Stop pressed after it.
