# Context parts

A context part is a part the new part must fit with. Today it is a variant the agent built. `propose_context_part(brief_id, quote, name, variant_id)` opens the stored variant, has the analysis container read its BREP, and stores a signed record with the part's facts: the number of solids, the volume in mm^3 and the bounding box in the part's own frame. It returns `part_id` (`part-` and the first 16 hex digits of the BREP's SHA-256), `status` and `facts`. The person confirms the part on the `ask_to_confirm` page, in a section titled "A part your design must fit with", and the same click confirms the requirements. `ask_to_confirm` then lists one item per part, `{kind: "context_part", part_id, name, outcome, box_min, box_max, note}`, after the requirements items. `score_variant` with a `brief_id` runs the `fit` check once per context part confirmed in the brief's project, in the background like `fea`. Its result carries the `part_id` as `instance` and measures `overlap_volume` (mm^3), `min_clearance` (mm), `context_solids` and `variant_solids`. It fails when the overlap is over 0.001 mm^3, and then `min_clearance` is 0. The variant is measured as built, so the agent builds it in the part's frame. A `min_clearance` or `max_clearance` requirement names the `part_id` and a length, and the fit check decides it. A variant that overlaps the part fails every clearance requirement on that part. `propose_requirements` refuses a `part_id` the project does not store, and a clearance requirement whose part is not confirmed is `unknown` with the reason "The context part is not confirmed, so the fit check did not measure against it." Without `brief_id` no fit runs.

Records live in `~/.cad/projects/<project_id>/context_parts/<n>.signed`, signed by the projects key. The geometry is `~/.cad/projects/<project_id>/parts/<brep_sha256>.brep`.

## Sub-features

- `part-live` makes Claude Code build a plate, store a brief that names it, propose requirements and the plate as a context part, and call `ask_to_confirm` while the scripted person confirms.
- `part-idempotent` proposes the same BREP twice. One record is stored and one item is listed.
- `part-declined` declines the part on the page. Proposing it again stores a second record that waits on a new page.
- `part-fit` builds a housing, confirms it with two `min_clearance` requirements, and scores a variant that overlaps it and a variant 0.5 mm clear of it.
- `part-fit-live` builds a rail, proposes it as a context part, confirms a brief with a `min_clearance` on it, builds a clip in the rail's frame and scores the clip with the `brief_id`. The card holds a `fit` result for the rail and the clearance verdict.
- `part-refusals` shows a quote that is not in the brief (`BadContextPart`), an unknown variant (`UnknownVariant`), a variant whose build failed (`NotBuilt`) and a shape the container refuses (`BadContextPart: variant <id> cannot be a context part: <reason>`). Nothing is stored for any of them.

## How to get to it (user POV)

Tell Claude Code that the new part must fit with a part it built earlier. The confirmation page shows that part, with the brief words it came from, its box and volume, and what the fit check will decide against it.

## Gotchas

- The part is identified by its BREP, not by its variant id. Two variants with the same geometry are the same part, and a rebuild under a new sandbox image keeps the part.
- `fit` measures the variant exactly where it was built. A clip built at the origin while the rail sits elsewhere passes with a large clearance, so a `max_clearance` stops a part that passes by sitting far away.
- A part has no number to change. A forged `edit-<i>-<row>` field for a part's item gets 400 and records nothing.
- A record or BREP edited on disk makes every call that reads the project's parts fail with `TamperedProject`. Only the operator can fix it, by deleting the project's context parts.
- Every scorecard has a `pending` key, so a poll loop tests `jq -e '.structuredContent.pending | length == 0'`, not a grep for `"pending"`. Check versions hash the check sources, so a rescore after an edit under `src/cad/checks/` gives a card the tracer reads as stale until it is scored again.
